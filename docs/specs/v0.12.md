# Yanshu v0.12：AI 与编辑器工具链

状态：实施中。当前已落地 formatter v1、稳定表达式节点路径、有界全局/局部符号索引、支持作用域感知 completion、同文档 definition/references、防捕获 rename、全文 semantic tokens 与版本化只读审查请求的最小 LSP 3.18 server、VS Code 无脚本审查面板、平台专用 VSIX 与 Windows/Linux Extension Host 验收、只读 Tree-sitter grammar、标准查询和差分语料门禁、兼容现代/旧版客户端的只读 stdio MCP，以及把 LSP/VSIX 纳入 v0.11 证据链的 release schema v3；结构化 AST 编辑仍未实现。v0.12 不改变 `.yan` language version v4，也不增加 guest capability。

## 1. 工具与语言的边界

`.yan` 源码、密封 Bundle manifest、package source 与 lock 仍是规范输入。formatter 只从已经通过 Reader/Parser 的单文件程序生成候选源码；它不能读取审查文本、Rust 投影或 LLM 自由文本并反向构造可执行程序。

格式化不会跳过语言版本门禁、类型/效果分析、fuel、测试或内容哈希。源码字节变化后，Bundle/package/VersionStore 必须按现有协议重新计算身份，不能沿用旧 hash。

## 2. formatter v1 契约

`yanshu-format` 提供纯 safe Rust 入口：

```rust
format_source(source: &str, options: FormatOptions) -> YanshuResult<FormattedSource>
```

默认边界是：

- 输入沿用 Reader 的 4 MiB source、64 KiB token、10,000 节点和 128 层嵌套上限；
- 输出最多 4 MiB，与正式 Reader source 上限一致，并在每次追加前检查上限；
- 行宽默认 100，可配置范围为 40..=240；
- 缩进默认 2，可配置范围为 1..=8；
- 所有列表分隔符规范化为圆括号，atom 与 string lexeme 保持不变；
- 行注释的文本与相对遍历顺序保留，行尾水平空白可被删除。

每次格式化按固定顺序失败关闭：

1. 检查配置和输入边界；
2. 使用正式 Reader/Parser 解析原程序；
3. 构建保留注释的 concrete tree 并生成布局；
4. 再用正式 Reader/Parser 解析输出；
5. 比较不含 span/source byte 的 `inspect_json`；
6. 比较注释内容与顺序；
7. 再格式化一次，要求输出逐字节相同。

任一步不满足都会返回稳定 `FORMAT_*` diagnostic，不会把候选文本冒充成功结果。

## 3. CLI 契约

```text
format <program.yan>
format <program.yan> --check
```

默认命令是只读的：JSON 返回 `formattedSource`、`changed` 与 `formatterVersion`，不会覆盖文件。`--check` 不返回完整源码；输入不是 formatter v1 规范布局时返回 `FORMAT_REQUIRED` 和非零退出码，适合 CI 与 Agent 门禁。

CLI 在读取前检查普通文件和大小，再以 `take(max + 1)` 限制实际读取。未来的原地写入或编辑器 WorkspaceEdit 必须先定义原子替换、并发修改检测和编码契约；当前版本不提供隐式写回。

## 4. 稳定表达式节点路径

`yanshu-syntax::expression_nodes` 为每个 definition 的表达式生成 `expression-v1/...` 语义路径。路径由 definition 名和结构角色组成，例如 `if/condition`、`let/body`、`call/argument/0`；它不包含 source offset，因此空白和注释格式化不会改变 ID。

节点 ID 是工具定位符，不是密码学内容哈希，也不是跨任意结构编辑永久不变的身份。definition 重命名、参数重排、分支插入等结构变化可以改变对应路径。每个节点仍同时携带当前源码 `Span`。

### 有界符号索引

`yanshu-syntax::local_symbol_index` 从已解析 Program 构建确定性的局部声明—引用索引；`symbol_index` 在相同规则上加入顶层 `def`。AST 决定作用域和解析顺序；对同一份、仍受 Reader 边界约束的规范源码执行第二次 Reader pass，只提取执行语义没有保存的 `def`、参数与 `let` 名称 span。两者结构不一致时返回 `TOOL_SYMBOL_SOURCE_MISMATCH`，不能搜索文本猜测声明位置。

索引覆盖全局 `def`、函数参数、顺序 `let` 和 match pattern binding。绑定表达式只能看见同一 `let` 中更早的名称；每个 match arm 有独立作用域；嵌套函数和内层 binding 按词法规则遮蔽外层，退出后恢复外层解析。全局定义的 signature、route handler 与 export 位置属于语义引用；其它引用必须是已解析变量表达式。字符串、注释、quote、类型、Schema 和未绑定原语不参与。声明与已解析引用的总数不能超过 Reader 节点上限。索引不改变 Program inspection、语言版本、执行、fuel、类型、效果或内容哈希；它是 references 与防捕获 rename 的共同语义基础。

## 5. 尚未实现

- lossless 增量语法树与跨编辑 identity reconciliation；
- 更多编辑器安装包及其 Tree-sitter/LSP 适配；
- LSP 局部增量同步、semantic token range/delta 与 code action；
- 结构化 AST diff 和受约束写回；
- Bundle/package 多文件批量格式化与原地写入。

这些功能不能用 Rust 审查文本反向解析、未计量宏或隐式宿主访问代替。

## 6. 最小 LSP 3.18 契约

`yanshu-lsp` 是独立 safe Rust stdio binary。它使用官方 LSP 3.18 的 JSON-RPC 2.0 `Content-Length` framing，并显式协商 `utf-16` position encoding。当前 capability 只有：

- full document sync：`didOpen`、`didChange`、`didClose`；
- Parser 诊断，以及 language v4 的类型/效果诊断；
- 精确 token hover：表达式/顶层/Schema/类型 form、core primitive、可信 Library operation、用户 definition 与局部 binding；函数类型、effect/capability、版本、fuel 合约和最深稳定 expression ID 按适用项显示；
- 作用域感知 completion：按当前位置提供可用 form、全局/局部 binding、版本化 core primitive、构造器、Schema、已声明可信 Library operation 和类型；
- 同文件全局 `def` 与局部参数、顺序 `let`、pattern binding 的 definition 跳转；
- 同文件、遵守 `includeDeclaration` 的全局/局部 references；
- 标准 `textDocument/semanticTokens/full`：为 namespace、类型、参数、变量、字段、构造器、函数、关键字和运算符返回只读语义分类；
- 同文件 `prepareRename` 与防捕获 rename；返回绑定打开快照版本的标准 `WorkspaceEdit.documentChanges`；
- 返回完整文档 `TextEdit[]` 的 canonical formatting；
- experimental `yanshu/reviewDocument`：从指定版本的打开快照返回 `rust-readonly-v3`、`editable:false`、显示语言和审查文本。

server 不读取 URI 对应的文件，不访问网络，不调用 provider，也不写回源码。编辑器决定是否应用 formatting edit。打开的文档快照是唯一分析输入。

协议和内存边界：

- 单条 JSON-RPC 消息最多 32 MiB，header 总计最多 16 KiB、32 行，单行最多 8 KiB；
- 单份 `.yan` 文本仍受 Reader 4 MiB 上限；
- 同时最多打开 32 份文档，总源码最多 16 MiB；
- 文档 URI 最多 4 KiB，version 必须单调递增；
- hover 文本最多 8 KiB，只返回命中 symbol 的 UTF-16 token range；
- completion 最多 128 项、所有候选文本合计最多 256 KiB；超限返回 `LSP_COMPLETION_LIMIT`，不静默截断；
- 单次 references 最多返回 1,024 个 Location，超过时以 `LSP_REFERENCE_LIMIT` 拒绝而不截断；
- 单次 semantic token 结果最多 10,000 项；每项固定五个 `u32`，超过时以 `LSP_SEMANTIC_TOKEN_LIMIT` 整体拒绝；
- 单次 rename 最多 1,024 处 edit，replacement 文本合计最多 4 MiB，候选源码仍不得超过 Reader 4 MiB；六倍 JSON 转义与逐项固定开销的编译期上界小于 32 MiB；
- review 请求只接受不超过 512 KiB 的打开快照，审查文本最多 4 MiB；版本不一致返回 `LSP_REVIEW_VERSION`，超限返回稳定 `LSP_REVIEW_*_LIMIT`；
- 只接受 full sync change；带 `range` 的增量 change 失败关闭；
- malformed framing 终止 stdio server，结构错误的 request 返回 JSON-RPC error，非法 notification 只输出不含源码的 `window/logMessage`。

hover、completion、definition 与 references 共用正式 AST 和上述有界符号索引。hover 先用同源 bounded Reader 定位一个精确 symbol token，再用 AST 节点、词法 binding、类型/效果报告或 `yanshu-library` 的可信 contract 决定含义；局部遮蔽先于 primitive，quote/string/comment 不冒充代码，索引失败时也不会猜宿主原语。内容固定为 plaintext，不含 Markdown HTML、command link、源码值、URI 或自由宿主文本，超出 8 KiB 时失败关闭。

completion 用 bounded Reader 确定光标处是顶层、表达式、类型还是 Schema，并只替换当前 symbol 的精确 UTF-16 range；comment、string 与 quote data 返回空结果。解析成功时，`SymbolIndex::visible_bindings_at` 按函数参数、顺序 `let`、match arm 和嵌套遮蔽返回当前位置真实可见的 binding；Reader 成功但 Program 尚未通过 Parser 时，只能从同一版本化 form 目录提供结构候选，不能搜索文本猜全局名称。core primitive 按 language version 过滤，`log/clock/kv` 还必须已由程序声明；Library operation 只从程序声明的精确版本 `trusted_contract` 产生。结果按稳定组别和名称排序，标签去重，返回 `isIncomplete:false`，不携带 snippet、command、自动 import 或跨文件 edit。超过 128 项或 256 KiB 候选文本时以 `LSP_COMPLETION_LIMIT` 整体失败关闭；六倍 JSON 转义与逐项固定开销的编译期上界仍小于 32 MiB protocol body。

semantic tokens 只实现标准全文请求，不声明 range、delta 或 `resultId`。顶层、类型、Schema、data 与 export token 由 bounded Reader 按正式 Parser 已接受的结构收集；表达式 special form 必须与 `expression_nodes` 的 AST span 对齐；全局 `def`、参数、顺序 `let` 和 pattern binding 必须来自 `SymbolIndex`。绑定分类优先于 primitive/Library，因此被局部名称遮蔽的 `log` 不会被染成默认库函数；字符串、注释和 quote data 不产生语义 token。结果按源码排序、去重且互不重叠，再用一次向前扫描编码为 UTF-16 相对五元组。解析失败返回 `null`，同源 span 或编码不一致返回稳定 `LSP_SEMANTIC_TOKEN_*` diagnostic，不会退化成正则或文本搜索。10,000 项与每项最坏 JSON 整数大小的编译期上界仍小于 32 MiB protocol body。

references 只返回当前打开文档，按源码顺序输出，是否包含声明由标准 `ReferenceContext.includeDeclaration` 决定；range 使用一次向前扫描转换为 UTF-16，不能为每个结果从文件头重复扫描。解析失败、索引与同源 span 不一致或名称不是可解析声明时返回空结果，不会退化成文本搜索。LSP 输出是开发工具数据，不参与 `.yan`、Bundle、package 或 VersionStore 内容哈希。

`prepareRename` 只在 `SymbolIndex` 已解析的声明或引用上返回精确 UTF-16 token range 与 placeholder；primitive、form、构造器、类型、Schema、字符串、注释和 quote 返回 `null`。`rename` 的 `newName` 必须由正式 bounded Reader 解析为恰好一个、逐字节相同的 symbol，空值、多 datum、字符串、数字、布尔和列表都以 `LSP_RENAME_NAME` 拒绝；新旧名称相同也不生成无意义 edit。

server 先收集目标 binding 的声明与全部已解析引用，并逐个核对源码切片，再在内存中生成候选 `.yan`。候选必须重新通过正式 Reader/Parser 和 `symbol_index`；重命名前每一个 binding 的种类、名称、变换后声明 span 与引用集合必须与候选完整符号图逐项相同。内层 binding 捕获改名后的引用、改名 binding 捕获原有引用、特殊 form 改变解析或其它符号解析变化都会以 `LSP_RENAME_CONFLICT` 整体拒绝，不返回部分 edit。边界溢出返回 `LSP_RENAME_LIMIT`，光标不在已解析 binding 或当前源码无法建立索引时返回 `LSP_RENAME_UNAVAILABLE`；诊断不回显源码或名称。

成功结果按源码顺序返回互不重叠的同文件 edit，并在 `TextDocumentEdit` 中携带 server 分析时的当前版本。server 不应用 edit、不写 URI 文件、不修改内存快照；编辑器只能把结果用于同一版本文档。rename 不接受 Rust 审查投影作为输入，也不改变语言执行、fuel、类型、效果、capability 或内容哈希规则。

`yanshu/reviewDocument` 只调用现有 Parser、类型/效果分析与单向 `render_rust_review`，不读取 URI 文件、不执行 guest、不写源码，也不返回可回写 edit。请求必须携带当前 `textDocument.version`；server 在分析前检查 512 KiB 预览输入边界，渲染后检查 4 MiB 文本边界，并以六倍 JSON 转义上界证明响应仍小于 32 MiB protocol body。renderer、`editable:false` 或版本任一不匹配都失败关闭。

## 7. VS Code 扩展与 VSIX 契约

`editors/vscode` 使用官方 `vscode-languageclient` 启动独立 Rust server，并声明 `.yan` language ID、括号/行注释配置与基础 TextMate grammar。TextMate 负责注释、字符串和基础词法回退，LSP semantic tokens 细化已解析代码中的关键词、类型、绑定与调用；两者都只是编辑器显示层，不参与 Parser、类型、效果、fuel 或内容哈希。

最低 VS Code 版本是 1.101：官方从该版本把 Node extension host 升级到 Node 22，与当前 language client 和 bundle target 保持一致。不能为了扩大安装范围而声明一个实际运行时不兼容的旧版本。

server 选择顺序固定为：

1. machine-scope `yanshu.server.path` 指定的绝对普通文件；
2. VSIX 内与当前 `platform-architecture` 精确匹配的 binary；
3. 宿主 `PATH` 中的 `yanshu-lsp`。

相对配置路径失败关闭，工作区设置不能替换 machine-scope server。扩展不运行 `cargo`、不执行工作区脚本，也不从 `.yan` 内容生成命令行。server 子进程环境会移除名称包含 `auth`、`credential`、`key`、`password`、`secret` 或 `token` 的变量。

`npm run package` 只接收当前宿主平台，打包前要求 release server 是不超过 128 MiB 的非 symlink 普通文件；extension client bundle 为单个 CommonJS 入口，VSIX 不携带开发依赖、Extension Host 测试 bundle 或散落的 `node_modules`，并只携带这一平台 binary 和 SHA-256/字节数 manifest。npm runtime/build 依赖精确固定并由 `package-lock.json` 绑定 integrity；打包器从生产依赖闭包生成排序、有界的第三方许可证正文，缺许可证、symlink 或超限时失败关闭。

release schema v3 在 Windows x86-64 与 Linux x86-64 各自把 `yanshu-lsp` 纳入双 target-dir 字节比对，并分别用两份独立 LSP 在固定 `SOURCE_DATE_EPOCH` 和精确锁定的 vsce 下生成平台 VSIX；两份 VSIX 必须逐字节相同。构建记录绑定 VSIX、平台和内含 LSP 的 SHA-256；CLI、MCP、LSP 的 Rust SBOM 与扩展生产 npm 图的第四份 SBOM一起进入 manifest/checksum/provenance 闭包。只有合入后新建、位于 `main` 且匹配 workspace 版本的注解式标签能发布这些资产；历史 Release 不补写，Marketplace 仍不在当前范围。

`yanshu.openRustReview` 仅在打开的 file/untitled `.yan` editor 上可用。扩展在旁侧创建 `yanshu.review` Webview Panel，而不是虚拟 `TextDocument` 或 `.rs` 文件：panel 没有编辑模型，关闭脚本，禁止本地资源根，使用 `default-src 'none'` CSP，并在插入 HTML 前转义源码标签与完整审查文本。面板最多 32 个；打开后对源码 full-sync change 做 250 ms 有界 debounce，只接受与当前版本相同的响应，旧响应不会覆盖新快照。loading/error 页面不回显 Parser、源码、URI 或 server 自由文本。

Extension Host 端到端测试固定使用最低兼容线的 VS Code 1.101.2，在系统临时目录组装最小扩展副本、release `yanshu-lsp` 和隔离的 user-data/extensions 目录。下载阶段可以沿用宿主代理，但启动测试进程前会移除 HTTP/HTTPS/ALL/NO_PROXY，并过滤名称包含 auth、credential、key、password、secret 或 token 的环境变量，同时关闭更新与遥测；Linux/Xvfb 所需的 `DISPLAY` 与 `XAUTHORITY` 除外。测试验证扩展激活、`.yan` language ID、诊断、用户函数类型/节点 hover、关键字语法 hover、全局函数/局部参数 completion 与精确替换范围、关键词/类型/函数/参数 semantic tokens、同文档全局/局部 definition/references、局部绑定 rename WorkspaceEdit、只返回 edit 的 formatting，以及审查命令打开无 `TextDocument` 的独立 Webview Panel。CI 在 Windows x64 与 Linux x64（Xvfb）分别运行测试、生成并暂存平台 VSIX。当前仍未发布到 Marketplace，也没有 macOS/Arm 平台矩阵，因此“Windows/Linux CI 可打包测试”不能表述为“已完成全平台发布验证”。

## 8. Tree-sitter 展示语法

`editors/tree-sitter-yanshu` 提供 v1-v4 的容错增量 CST，覆盖 Reader 的 `()`、`[]`、`{}` 等价列表分隔符、注释、字符串转义、quote datum，以及当前 program、Schema、type、expression 与 pattern 结构。包同时提供标准 `highlights.scm`、`locals.scm`、`folds.scm` 和 `tags.scm`。

Tree-sitter 不是语言验证器。它不实施 language-version gate、声明唯一性、顺序 `let` 的精确可见性、类型/effect、capability、fuel、内容哈希或 Bundle 链接规则；容错树中的节点不能进入执行、密封、晋升或结构化写回。精确 hover、semantic tokens、definition/references 与 rename 继续使用正式 AST 和 `SymbolIndex`。

grammar 使用精确锁定的 Tree-sitter CLI 生成 C parser，但生成 C 只属于编辑器生态包。第一方 Rust crate 不链接它，也不提供需要 `unsafe` 的 Rust binding。生成 parser 不是沙箱，也没有 Yanshu fuel/内存计量；具体编辑器适配必须在解析前实施文档大小上限，兼容入口应沿用 Reader 的 4 MiB source ceiling。

CI 在 Windows/Linux 重新生成并比较制品、运行 corpus 与四组 query，并让 Tree-sitter 和 formatter 的正式 Reader/Parser 往返路径接受同一组有界仓库源码；这只能证明展示语法没有偏离当前有效语料，不能替代 conformance 或 Parser 的拒绝测试。

## 9. 只读 MCP / Agent Tool Protocol

`yanshu-mcp` 是独立 safe Rust stdio binary。它只暴露三个工具：

- `yanshu.inspect_source`：正式 Reader/Parser inspection，v4 同时运行类型/效果与 capability 分析；
- `yanshu.format_source`：返回 formatter v1 候选、变化标记和 formatter 版本；
- `yanshu.review_source`：返回分析报告与 `rust-readonly-v3` 文本/nodes。

所有输入都是当前完整 `.yan` 源码字符串。协议不接受路径、URI 或 workspace root，不读取文件和环境凭据，不访问网络/provider，不执行 guest，也没有写回工具。Agent 必须用自己的受控文件能力读取和应用候选；MCP 不能绕过 Parser、类型/效果、Bundle/package 哈希或测试门禁。

stdio framing 是一行一个 UTF-8 JSON-RPC 对象。server 同时实现：

- MCP `2026-07-28`：校验每个 request 的 protocol version/client capabilities `_meta`，支持 `server/discover`，结果带 `resultType` 与 server info；
- legacy `2025-11-25`、`2025-06-18`、`2025-03-26`、`2024-11-05`：通过 `initialize` 协商后处理 `tools/list`、`tools/call` 和 `ping`。

未知 tool、畸形 request 和未初始化 legacy 调用返回标准 JSON-RPC error，并在 `data.yanshuCode` 携带稳定机器码。Reader、Parser、类型、formatter 或 review 失败属于工具执行错误，以 `isError:true` 返回 `Diagnostic::public_json()`；成功和工具错误都同时提供 `structuredContent` 与内容相同的 JSON TextContent，兼容只读取文本的旧客户端。server stdout 不输出日志或自由文本。

边界固定为：

- 单条输入 4 MiB，必须有 newline；单条输出 32 MiB；
- tool source 512 KiB，最坏六倍 JSON 转义加固定请求开销仍小于输入上限；
- formatter source/output 512 KiB，并继续应用 Reader token/string/node/depth 上限；
- review text 4 MiB，序列化 tool payload 8 MiB；
- `structuredContent` 与兼容 TextContent 的最坏三倍序列化开销加固定响应开销小于 32 MiB；
- 请求串行处理；oversized/unterminated framing 发送有界 parse error 后终止，已消费完整行的非法 JSON 可恢复到下一条消息。

工具 schema 拒绝额外参数，并声明 read-only、non-destructive、idempotent、closed-world annotations。formatter/review 继续单向使用权威 AST；MCP 文本不能成为规范输入或可执行 Rust。
