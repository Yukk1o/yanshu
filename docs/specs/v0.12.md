# Yanshu v0.12：AI 与编辑器工具链

状态：实施中。当前已落地 formatter v1、稳定表达式节点路径、最小 LSP 3.18 server、平台专用 VS Code VSIX 与 Windows/Linux Extension Host 验收；Tree-sitter、MCP 和结构化 AST 编辑仍未实现。v0.12 不改变 `.yan` language version v4，也不增加 guest capability。

## 1. 工具与语言的边界

`.yan` 源码、密封 Bundle manifest、package source 与 lock 仍是规范输入。formatter 只从已经通过 Reader/Parser 的单文件程序生成候选源码；它不能读取审查文本、Rust 投影或 LLM 自由文本并反向构造可执行程序。

格式化不会跳过语言版本门禁、类型/效果分析、fuel、测试或内容哈希。源码字节变化后，Bundle/package/VersionStore 必须按现有协议重新计算身份，不能沿用旧 hash。

## 2. formatter v1 契约

`yanshu-format` 提供纯 safe Rust 入口：

```rust
format_source(source: &str, options: FormatOptions) -> YanshuResult<FormattedSource>
```

默认边界是：

- 输入沿用 Reader 的 4 MiB source、64 KiB token、10,000 节点和 128 层嵌套上限；
- 输出最多 4 MiB，与正式 Reader source 上限一致，并在每次追加前检查上限；
- 行宽默认 100，可配置范围为 40..=240；
- 缩进默认 2，可配置范围为 1..=8；
- 所有列表分隔符规范化为圆括号，atom 与 string lexeme 保持不变；
- 行注释的文本与相对遍历顺序保留，行尾水平空白可被删除。

每次格式化按固定顺序失败关闭：

1. 检查配置和输入边界；
2. 使用正式 Reader/Parser 解析原程序；
3. 构建保留注释的 concrete tree 并生成布局；
4. 再用正式 Reader/Parser 解析输出；
5. 比较不含 span/source byte 的 `inspect_json`；
6. 比较注释内容与顺序；
7. 再格式化一次，要求输出逐字节相同。

任一步不满足都会返回稳定 `FORMAT_*` diagnostic，不会把候选文本冒充成功结果。

## 3. CLI 契约

```text
format <program.yan>
format <program.yan> --check
```

默认命令是只读的：JSON 返回 `formattedSource`、`changed` 与 `formatterVersion`，不会覆盖文件。`--check` 不返回完整源码；输入不是 formatter v1 规范布局时返回 `FORMAT_REQUIRED` 和非零退出码，适合 CI 与 Agent 门禁。

CLI 在读取前检查普通文件和大小，再以 `take(max + 1)` 限制实际读取。未来的原地写入或编辑器 WorkspaceEdit 必须先定义原子替换、并发修改检测和编码契约；当前版本不提供隐式写回。

## 4. 稳定表达式节点路径

`yanshu-syntax::expression_nodes` 为每个 definition 的表达式生成 `expression-v1/...` 语义路径。路径由 definition 名和结构角色组成，例如 `if/condition`、`let/body`、`call/argument/0`；它不包含 source offset，因此空白和注释格式化不会改变 ID。

节点 ID 是工具定位符，不是密码学内容哈希，也不是跨任意结构编辑永久不变的身份。definition 重命名、参数重排、分支插入等结构变化可以改变对应路径。每个节点仍同时携带当前源码 `Span`。

## 5. 尚未实现

- lossless 增量语法树与跨编辑 identity reconciliation；
- Tree-sitter grammar、语义高亮与更多编辑器安装包；
- LSP 局部增量同步、局部 binding definition、completion、rename、references、semantic tokens 与 code action；
- 只读 MCP/Agent 工具协议；
- 结构化 AST diff 和受约束写回；
- Bundle/package 多文件批量格式化与原地写入。

这些功能不能用 Rust 审查文本反向解析、未计量宏或隐式宿主访问代替。

## 6. 最小 LSP 3.18 契约

`yanshu-lsp` 是独立 safe Rust stdio binary。它使用官方 LSP 3.18 的 JSON-RPC 2.0 `Content-Length` framing，并显式协商 `utf-16` position encoding。当前 capability 只有：

- full document sync：`didOpen`、`didChange`、`didClose`；
- Parser 诊断，以及 language v4 的类型/效果诊断；
- definition 内的类型、capability effect 与最深稳定 expression ID hover；
- 不会把词法局部 binding 误跳到同名全局 definition 的全局跳转；
- 返回完整文档 `TextEdit[]` 的 canonical formatting。

server 不读取 URI 对应的文件，不访问网络，不调用 provider，也不写回源码。编辑器决定是否应用 formatting edit。打开的文档快照是唯一分析输入。

协议和内存边界：

- 单条 JSON-RPC 消息最多 32 MiB，header 总计最多 16 KiB、32 行，单行最多 8 KiB；
- 单份 `.yan` 文本仍受 Reader 4 MiB 上限；
- 同时最多打开 32 份文档，总源码最多 16 MiB；
- 文档 URI 最多 4 KiB，version 必须单调递增；
- 只接受 full sync change；带 `range` 的增量 change 失败关闭；
- malformed framing 终止 stdio server，结构错误的 request 返回 JSON-RPC error，非法 notification 只输出不含源码的 `window/logMessage`。

全局 definition 跳转使用 Reader 保存的 definition name span。局部参数、`let` 和 pattern binding 当前只用于阻止错误跳转，尚不返回局部声明位置。LSP 输出是开发工具数据，不参与 `.yan`、Bundle、package 或 VersionStore 内容哈希。

## 7. VS Code 扩展与 VSIX 契约

`editors/vscode` 使用官方 `vscode-languageclient` 启动独立 Rust server，并声明 `.yan` language ID、括号/行注释配置与基础 TextMate grammar。高亮只是编辑器显示层，不参与 Parser、类型、效果、fuel 或内容哈希。

最低 VS Code 版本是 1.101：官方从该版本把 Node extension host 升级到 Node 22，与当前 language client 和 bundle target 保持一致。不能为了扩大安装范围而声明一个实际运行时不兼容的旧版本。

server 选择顺序固定为：

1. machine-scope `yanshu.server.path` 指定的绝对普通文件；
2. VSIX 内与当前 `platform-architecture` 精确匹配的 binary；
3. 宿主 `PATH` 中的 `yanshu-lsp`。

相对配置路径失败关闭，工作区设置不能替换 machine-scope server。扩展不运行 `cargo`、不执行工作区脚本，也不从 `.yan` 内容生成命令行。server 子进程环境会移除名称包含 `auth`、`credential`、`key`、`password`、`secret` 或 `token` 的变量。

`npm run package` 只接收当前宿主平台，打包前要求 release server 是不超过 128 MiB 的非 symlink 普通文件；extension client bundle 为单个 CommonJS 入口，VSIX 不携带开发依赖、Extension Host 测试 bundle 或散落的 `node_modules`，并只携带这一平台 binary 和 SHA-256/字节数 manifest。npm runtime/build 依赖精确固定并由 `package-lock.json` 绑定 integrity；打包器从生产依赖闭包生成排序、有界的第三方许可证正文，缺许可证、symlink 或超限时失败关闭。

Extension Host 端到端测试固定使用最低兼容线的 VS Code 1.101.2，在系统临时目录组装最小扩展副本、release `yanshu-lsp` 和隔离的 user-data/extensions 目录。下载阶段可以沿用宿主代理，但启动测试进程前会移除 HTTP/HTTPS/ALL/NO_PROXY，并过滤名称包含 auth、credential、key、password、secret 或 token 的环境变量，同时关闭更新与遥测；测试验证扩展激活、`.yan` language ID、诊断、hover、同文档全局 definition 和只返回 edit 的 formatting。CI 在 Windows x64 与 Linux x64（Xvfb）分别运行测试、生成并暂存平台 VSIX。当前仍未发布到 Marketplace，也没有 macOS/Arm 平台矩阵，因此“Windows/Linux CI 可打包测试”不能表述为“已完成全平台发布验证”。
